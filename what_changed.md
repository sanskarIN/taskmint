## Work completed in the latest continuation

### 1. Lossless CSV tag encoding

A real data-loss bug was found in the original CSV representation.

Previous behavior:

- CSV export serialized task tags with `task.tags.join('|')`.
- CSV import split the field with `.split('|')`.
- The domain allows `|` inside a tag.
- Therefore a valid single tag such as `ci|cd` could be exported and re-imported as two different tags (`ci`, `cd`).

The CSV format is now backward compatible and lossless:

- New TaskMint CSV exports encode the tag cell as `json:` followed by a JSON array.
- Example conceptual form: `json:["ci|cd","release"]`.
- CSV quoting still handles the JSON double quotes correctly.
- New imports recognize the explicit `json:` prefix and parse the payload as an array of strings.
- Malformed new structured tag payloads are rejected instead of silently falling back to a different interpretation.
- Older pipe-separated CSV files remain importable for backward compatibility.
- A new stable typed error code `csv-invalid-tags` exists for malformed structured tag content.

### 2. Spreadsheet-formula injection hardening for CSV exports

User-controlled CSV text can be opened by spreadsheet software. Values beginning with formula-trigger characters may be interpreted as formulas by some spreadsheet applications instead of plain text.

New TaskMint CSV exports now use a reversible safe-text encoding for user-controlled text fields:

- Protected fields: task title, notes, project.
- Formula-trigger characters handled: `=`, `+`, `-`, `@`.
- Formula-trigger characters are also detected after leading spaces, tabs, carriage returns, or newlines. This matters because imported JSON backup-shaped notes can retain leading whitespace even though normal interactive task creation trims it.
- Values beginning with a literal apostrophe are escaped reversibly too.
- New exports append a `taskmintEncoding` column with value `safe-text-v1`.
- TaskMint decodes the reversible protection only when this explicit encoding marker is present.
- Legacy CSV files without the marker keep their original semantics and are not reinterpreted by the new decoder.
- Structured `json:` tag cells do not require spreadsheet-formula escaping because they begin with a fixed safe prefix.

This protects spreadsheet opening while still allowing TaskMint-generated CSV files to round-trip the intended task text according to normal CSV task normalization rules.

### 5. True atomicity for every multi-task persistence operation

A release-critical reliability bug was identified by auditing Dexie bulk-operation semantics.

Previous `TaskRepository.putTasks(...)` called `database.tasks.bulkPut(tasks)` directly. Dexie documents that a bulk operation outside a surrounding transaction can persist successful rows even when another row fails.

That meant code paths expected to behave as all-or-nothing could theoretically leave partial writes:

- CSV import.
- Recurring completion + generated next occurrence.
- Keyboard reorder batches.
- Drag reorder batches.

`putTasks(...)` now:

- Returns immediately for an empty batch.
- Opens an explicit `rw` Dexie transaction over the task table.
- Performs `bulkPut(...)` inside that transaction.
- Propagates failure so the transaction aborts instead of treating a partially successful batch as success.

New `tests/repository.test.ts` verifies:

- `putTasks` uses a read-write transaction.
- The batch is passed to `bulkPut` inside the transaction scope.
- A bulk failure propagates.
- An empty batch avoids an unnecessary transaction.

Relevant commits:

- `9fc19a3bee9c7ec37e44660328ccf956c497fcf3` — `fix: make bulk task writes atomic`

### 8. Large-data-safe manual order allocation

Another large-import edge was found in `App.tsx`.

Previous code used:

```ts
Math.max(0, ...tasks.map((task) => task.order)) + 1000
```

At the allowed 100,000-task import boundary, spreading a large array into a function call can hit JavaScript engine argument-count limits.

New file: `src/domain/order.ts`.

`nextTaskOrder(...)` now:

- Iterates through task order values.
- Tracks the maximum using constant call-stack/argument space.
- Returns maximum + configured step.
- Avoids allocating a second `tasks.map(...)` array solely for order calculation.

`App.tsx` now calls `nextTaskOrder(tasks)` when creating a task.

New `tests/order.test.ts` verifies:

- first-order behavior
- a 100,000-entry input
- a custom positive step

## Previous RC3 hardening retained

All previous hardening remains present, including the following.

### Typed user-safe errors

`src/domain/errors.ts` owns stable `TaskMintErrorCode`, structured details, immutable details, default safe messages, and `fail(...)`.

`src/i18n/errors.ts` exposes detailed validation errors only for known `TaskMintError` values and uses generic product fallback text for unknown browser/IndexedDB/Dexie/infrastructure errors.

TaskComposer and import paths use this safe boundary.

### Strict task/backup/CSV validation

Shared limits remain centralized in `src/domain/limits.ts`:

- ID 100
- title 240
- notes 20,000
- project 80
- tags per task 12
- tag length 32
- backup/import tasks 100,000
- import file/text boundary 25,000,000

Validation rejects:

- malformed/unsupported backup shape
- duplicate IDs
- impossible dates
- malformed timestamps
- invalid enum values
- invalid status/timestamp combinations
- invalid/non-finite order values
- malformed settings
- invalid tag elements
- excess tag count/length
- oversized fields
- malformed CSV quotes/headers/enums/dates/tasks
- malformed structured tag cells

### Deterministic canonical tags

Persisted/restored tags use locale-independent Unicode lowercase instead of host-locale lowercase, preventing canonical stored values from changing with OS/browser locale.

### Test isolation

`src/test/setup.ts` performs shared after-each cleanup:

- Testing Library cleanup
- real-timer restoration
- mock history clearing
- global un-stubbing
- spy/mock restoration

This fixed a real earlier `crypto.randomUUID` stub leakage issue.

### Download lifecycle

`downloadText(...)` defers object-URL revocation until the next timer turn after the download click. `tests/download.test.ts` verifies the sequence.

### Reminder persistence consistency

Reminder notification suppression is reset only after an edited reminder has been successfully persisted. Failed writes cannot make the unchanged old reminder eligible for duplicate notification.

### Date rollover/session freshness

`App.tsx` refreshes date-sensitive state:

- every 60 seconds
- on window focus
- on document visibility change

Today/Upcoming/Overdue and productivity statistics therefore refresh across midnight without requiring another task mutation.

### Production CSP separation

Committed production HTML remains restrictive:

- `default-src 'self'`
- `script-src 'self'`
- `style-src 'self'`
- `img-src 'self' data:`
- `connect-src 'self'`
- `manifest-src 'self'`
- `object-src 'none'`
- `base-uri 'self'`
- `form-action 'self'`

Vite development-only inline style and WebSocket allowances are injected only by an `apply: 'serve'` development transform.

### Repository hygiene gates

Dependency-free repository checks remain available:

- `npm run format:check`
- `npm run docs:check`
- `npm run secrets:check`

Benchmark files are included in formatting and secret-pattern scanning.

### Notification failure isolation

Browser Notification constructor failures are isolated per reminder. A failed construction does not break the polling loop and does not mark the reminder as delivered, so a later poll may retry.

### Privacy disclosures

Privacy documentation explicitly covers:

- local IndexedDB task/settings data
- notification title exposure to browser/OS surfaces
- downloaded JSON/CSV files existing outside IndexedDB
- browser/site-data deletion not removing downloaded backups
- no required TaskMint backend/account
- static PWA update requests not intentionally including task content
