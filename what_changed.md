## RC7 deep hardening completed in this continuation

### 1. Task composer submissions are serialized

The task form previously allowed more than one submit event to enter the same asynchronous save while IndexedDB persistence was pending. Rapid click/keyboard submission could therefore race duplicate creates or repeated updates.

`src/components/TaskComposer.tsx` now has:

- synchronous `submitLock` ref
- visible `submitting` state
- `aria-busy`
- disabled submit/input/detail/cancel controls while persistence is pending
- `finally` cleanup so failure remains retryable

Regression coverage verifies two immediate form submissions call the persistence callback once and controls re-enable after completion.

Commits:

- `edb097e7a29f03866fa54765ea7d869a4d701dae` — `fix: serialize task composer submissions`
- `5599bebba057a0582322049fa734649aa91b2605` — `test: cover duplicate composer submission lock`

### 2. Task-row mutations are serialized

Task cards previously exposed independent asynchronous controls without a per-row pending-operation guard. Rapid repeated completion was especially risky for recurring tasks because it could create more than one next occurrence before React state caught up.

`src/components/TaskItem.tsx` now serializes:

- complete/reopen
- archive
- restore
- delete
- keyboard move up/down
- drag/drop mutation

While a row mutation is pending:

- the row exposes `aria-busy`
- mutation controls are disabled
- drag is disabled
- a second mutation callback cannot enter even in the same tick because the ref lock is synchronous

Commits:

- `76b17f453b8a2a9911d79be804644a4fe3f1c15d` — `fix: serialize task row mutations`
- `e057f1b42db128738c3af272445a55507f14decc` — `test: cover task row mutation lock`

### 3. Repository writes now validate before persistence

Validated reads alone were insufficient because runtime callers can bypass TypeScript at JavaScript boundaries or through future code changes.

`TaskRepository` now validates before writing:

- `putTask` -> `validateTask`
- `putTasks` -> validate the complete batch before opening the transaction
- `replaceAllTasks` -> validate the complete replacement before clearing current tasks
- `saveSettings` -> `validateSettings`

Malformed values are rejected before they enter IndexedDB.

Commits:

- `a0660603794233c83b0d337e1ec4bc65df9aa228` — `fix: validate records before local persistence`
- `8c4750aff8dbc6266fa28df44294a338a86c9b37` — `test: cover repository write validation`

### 4. Backup restore has a non-destructive preflight boundary

`restoreBackup` now executes complete `validateBackup(...)` validation before opening the Dexie read-write transaction that clears/replaces tasks.

This means malformed runtime backup objects cannot reach the destructive transaction scope. The validation pass also preserves existing backup normalization rules before persistence.

Regression coverage proves a malformed restore fails before the transaction and before any task/settings clear operation.

Commits:

- `a0760bd2610e10ebcacd23196c722bf6d1c1ef67` — `fix: preflight backup restores before clearing data`
- `1e1533aa64b06345ad4140ad35a4ac838a55e279` — `test: verify restore preflight is non-destructive`

### 5. Development event metadata now fails closed with an explicit identifier-key allowlist

The previous `logEvent` implementation redacted known sensitive key names, but an arbitrary string or nested object under an unrecognized key could still contain user task content.

The first RC7 hardening pass retained strings whenever a key matched `/id$/i`. A deeper static review found that ordinary words such as `valid` and `grid` also end with the letters `id`, so that pattern was too permissive.

`src/utils/logger.ts` now keeps only explicitly safe diagnostic shapes:

- `null`
- booleans
- numbers
- identifier strings only when both the key and value match restricted identifier patterns

Allowed identifier key forms are intentionally narrow:

- `id`
- camel/Pascal-style `...Id` or `...ID`
- snake-case `..._id`

Identifier values must match:

- `[A-Za-z0-9._:-]{1,128}`

Everything else is replaced with `[REDACTED]`, including:

- arbitrary strings
- arrays
- nested objects
- known sensitive keys such as title/notes/token/secret/password/cookie/authorization
- unsafe identifier strings containing spaces/content
- lookalike ordinary keys such as `valid` and `grid`

`logError` retains the earlier coarse error-kind/stable-code behavior and does not print arbitrary exception messages.

Commits:

- `0b35e5e5fb3fd232e4e27212a9cf29db80f30e2f` — `test: cover fail-closed event metadata logging`

### 6. Bulk persistence rejects duplicate task IDs

A bulk task array containing the same ID twice could otherwise use IndexedDB/Dexie last-write-wins semantics and hide a caller defect.

Added typed error:

- `task-batch-duplicate-id`

Repository batch validation now:

1. validates every task
2. checks the complete ID set
3. rejects a duplicate before opening the transaction

The typed error contract now also has a direct regression that verifies its stable code, message, and structured `id` detail.

- `5970f334d9cea0653002af3ac11059a1578e0beb` — `fix: reject duplicate ids in task batches`

- `67d4ff739869d3b69a0238b965b3e4848c94fb94` — `test: cover duplicate task batch error contract`

### 7. Settings/data operations are serialized

The Settings dialog could start overlapping theme, accessibility, notification, export, import, and deletion operations while a previous asynchronous action was pending. That could combine stale `settings` props with competing storage work.

`src/components/SettingsDialog.tsx` now has a synchronous `actionLock` plus accessible busy state. While an action is pending:

- controls that can start another Settings/data action are disabled
- hidden import inputs are disabled
- close is disabled
- Escape cannot dismiss the dialog
- backdrop dismissal is blocked
- same-tick dismissal is guarded by the ref lock, not only asynchronous React state

Commits:

- `58441682aa0f59fa7e9f99aa284c3a69426b0075` — `fix: serialize settings and data actions`
- `80a6d60ce07b141fc47d0e61d10025fa044cc0dc` — `test: cover serialized settings actions`
- `8954ca44fbfebc7fcc0869228c7cc23ba5745109` — `fix: guard settings dismissal with action lock`

### 8. Onboarding completion is serialized

The onboarding Start action persists settings asynchronously. It now uses a synchronous completion lock so repeated activation cannot schedule multiple competing settings writes.

The dialog exposes `aria-busy`, the Start control is disabled while pending, safe failure copy remains intact, and the action becomes retryable after completion/failure.

Commits:

- `190f2f86a887f8479870e99aa4b2f4abe5394c96` — `fix: serialize onboarding completion`
- `ab97ff7149ccb76fc9d8f2b6685e9a07e4845b08` — `test: cover onboarding completion lock`

### 9. PWA update activation is serialized

The explicit Update now control could previously call `updateServiceWorker(true)` repeatedly while activation was pending.

`src/components/PwaUpdatePrompt.tsx` now:

- uses a synchronous activation lock
- exposes `aria-busy`
- disables Update now and Later during activation
- releases the lock in `finally`
- preserves safe retry behavior after activation failure
