# RC7 hardening completed

## 1. TaskComposer duplicate-submit protection

`src/components/TaskComposer.tsx` now prevents rapid duplicate create/update submission while persistence is pending.

Implemented:

- synchronous `submitLock`
- submitting state
- `aria-busy`
- disabled form controls during the pending write
- disabled cancel during pending write
- external `disabled` support for the App-wide task mutation lock
- safe retry after failure through `finally` cleanup

Tests verify:

- two immediate form submissions enter `onSubmit` only once
- controls disable while pending and re-enable afterward
- an App-wide external lock prevents submission without clearing the draft
- edit completion still clears stale edited values correctly

Key commits include:

- `edb097e7a29f03866fa54765ea7d869a4d701dae` — `fix: serialize task composer submissions`
- `5599bebba057a0582322049fa734649aa91b2605` — `test: cover duplicate composer submission lock`

## 2. Task-row duplicate-mutation protection

`src/components/TaskItem.tsx` now serializes each row's asynchronous mutation controls.

Protected actions:

- complete
- reopen
- archive
- restore
- delete
- keyboard move up/down
- drag/drop mutation

Implemented:

- synchronous row `mutationLock`
- local busy state
- `aria-busy`
- external `disabled` support for the App-wide task mutation lock
- drag disabled while local or App-wide mutation work is pending
- edit/reorder/archive/delete/restore/complete controls disabled while blocked

This prevents the same row from producing duplicate recurring occurrences or competing writes before React state catches up.

Key commits:

- `76b17f453b8a2a9911d79be804644a4fe3f1c15d` — `fix: serialize task row mutations`
- `e057f1b42db128738c3af272445a55507f14decc` — `test: cover task row mutation lock`

## 3. App-wide exclusive task mutation gate

Per-component locks alone could not prevent two different task cards from starting competing writes from the same stale `tasks` snapshot.

A reusable exclusive gate now exists in:

- `src/utils/mutation.ts`

The App owns one synchronous task mutation ref plus visible busy state. The same gate now covers:

- create task
- edit task
- complete task
- reopen task
- archive task
- restore task
- delete task
- undo delete
- keyboard reorder
- drag/drop reorder

While an App-wide task mutation is pending:

- TaskComposer is externally disabled
- all rendered TaskItem actions are externally disabled
- the task list exposes busy state
- Settings cannot be opened
- global task/search shortcuts are blocked
- Undo cannot start a competing task mutation

The reusable gate:

- rejects/ignores competing work before the second action is entered
- can surface a caller-provided safe busy error when the caller must retry
- always releases after action failure
- also releases if entering the busy UI state itself throws synchronously

`tests/AppMutation.test.tsx` performs an App-level cross-row regression: one task persistence call is intentionally held pending, a second different task is activated, and only the first write is allowed. After release, the second row becomes usable and can persist normally.

This closes the stale-cross-row snapshot race rather than only suppressing double-clicks on a single card.

## 4. Collision-free recurring occurrence ordering

A recurring task previously defaulted the next occurrence's manual order to `now.getTime()`. That could collide with an existing safe-integer order slot.

`completeTask(...)` / `makeNextOccurrence(...)` now support an explicit next order.

The App supplies:

- `nextTaskOrder(tasks)`

for recurring completion, so the generated next occurrence is placed after the current maximum task order instead of relying on clock milliseconds.

Tests verify:

- a caller-provided order is used exactly
- a non-safe-integer recurrence order is rejected
- existing default behavior remains available for isolated domain callers

## 5. Repository write-boundary validation

`src/storage/repository.ts` now validates records at the persistence boundary, not only when reading them later.

Implemented:

- `putTask` -> `validateTask`
- `putTasks` -> validate the entire batch before opening the transaction
- `replaceAllTasks` -> validate the entire replacement before clearing existing data
- `saveSettings` -> `validateSettings`

Malformed runtime values are rejected before entering IndexedDB.

Key commits:

- `a0660603794233c83b0d337e1ec4bc65df9aa228` — `fix: validate records before local persistence`
- `8c4750aff8dbc6266fa28df44294a338a86c9b37` — `test: cover repository write validation`

## 6. Non-destructive backup restore preflight

`TaskRepository.restoreBackup(...)` now validates and normalizes the complete backup before opening the destructive Dexie transaction.

Therefore malformed input cannot reach the clear/write phase.

Existing `validateBackup(...)` already normalizes duplicate manual-order slots before returning the restored backup. During the second audit this path was rechecked and deliberately left unchanged because it was already correct; no redundant churn was added.

Regression coverage verifies a malformed backup fails before:

- transaction open
- task clear
- settings clear

Key commits:

- `a0760bd2610e10ebcacd23196c722bf6d1c1ef67` — `fix: preflight backup restores before clearing data`
- `1e1533aa64b06345ad4140ad35a4ac838a55e279` — `test: verify restore preflight is non-destructive`

## 7. Duplicate task IDs rejected before bulk persistence

A bulk array containing the same task ID more than once could otherwise depend on IndexedDB/Dexie last-write-wins behavior.

Added stable typed error:

- `task-batch-duplicate-id`

Repository batch validation now:

1. validates every task
2. checks the complete ID set
3. rejects duplicates
4. only then opens the write transaction

The typed error contract is directly tested for:

- code
- message
- structured `id` details

Key commits:

- `1605716279fc27e9fe2e7f1c6db93fb3e5fcfc23` — `refactor: add duplicate task batch error`
- `5970f334d9cea0653002af3ac11059a1578e0beb` — `fix: reject duplicate ids in task batches`
- `58adbdcf6bcc41e078e2cf34b8eaa438bcc322e8` — `test: reject duplicate ids before bulk persistence`
- `67d4ff739869d3b69a0238b965b3e4848c94fb94` — `test: cover duplicate task batch error contract`

## 8. CSV record-number correctness after blank records

CSV imports intentionally skip completely blank logical records. The earlier processing order filtered blank records before assigning validation row numbers, so an error after a blank record could report the wrong source record.

The parser pipeline now:

1. preserves the original logical record index
2. associates `rowNumber` before filtering blanks
3. skips blank records
4. passes the original record number into task parsing/validation

Regression coverage verifies that an invalid record physically/logically at row 3 is still reported as row 3 even when row 2 is blank.

Commits:

- `5049a368c35a22c21d2a1e008cdcb77c0c53fec3` — `fix: preserve CSV record numbers after blank rows`
- `149d1fca7cd7477e58c43700411ccb6a4ab10112` — `test: preserve CSV error row after blanks`

## 9. Collision-free CSV merge ordering

CSV-created tasks previously derived manual-order values from the current clock and then merged into existing tasks. The imported task itself could be valid while still colliding with an existing manual-order slot.

`csvToTasks(...)` now accepts an optional caller-provided first order and assigns valid imported records contiguous orders from that base.

The App now calls:

- `csvToTasks(csvText, nextTaskOrder(tasks))`

Therefore a CSV merge begins strictly after the current maximum order and blank records do not create order gaps in the imported sequence.

Regression coverage verifies caller-provided order rebasing across skipped blank records.

Commits:

- `99f1bcc8ec56f3a7734aaf0f665d92ecdaa15463` — `feat: support collision-free CSV order rebasing`
- `fb7d728a67e5bd7ef002415b5ea52579ca3c6e35` — `test: cover rebased CSV import ordering`
- `26b0709d1a343792084dda7fe1637eeac9b4eae9` — `fix: rebase CSV imports after existing task orders`

## 13. Development diagnostic metadata fails closed

Development diagnostics must not accidentally print task content or arbitrary exception details.

`logError(...)` continues to emit only:

- coarse error kind, or
- stable `TaskMintError` code

It does not print arbitrary `Error.message` content.

`logEvent(...)` now retains only explicitly safe metadata shapes:

- `null`
- booleans
- numbers
- restricted identifier strings under restricted identifier key forms

Allowed identifier key forms are narrowly constrained to:

- `id`
- camel/Pascal `...Id` or `...ID`
- snake-case `..._id`

Identifier values must match:

- `[A-Za-z0-9._:-]{1,128}`

All other strings, arrays, nested objects, unsafe identifier values, and explicitly sensitive keys are replaced with `[REDACTED]`.

A deeper audit caught and fixed an earlier overly broad `/id$/i` pattern that would also match ordinary words such as `valid` or `grid`.

Key commits:

- `6509c65f55341e1f795856a170106ed4d8775750` — `fix: fail closed for diagnostic event metadata`
- `0b35e5e5fb3fd232e4e27212a9cf29db80f30e2f` — `test: cover fail-closed event metadata logging`
- `4d6db22f67dc417da529c8bea5dca224240373fe` — `security: restrict diagnostic identifier keys`
- `1979d2e240e33fb2170f9bf121938bcc64802f94` — `test: reject lookalike diagnostic id keys`
